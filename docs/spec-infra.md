# spec-infra.md (Дополнение к ТЗ: NFR, observability, эксплуатация)

Файл содержит инфраструктурные ограничения и эксплуатационные договорённости, вытекающие из `tz_tactical_app.md`.
Это инженерная детализация (NFR, аудит, deployment, фоновые задачи), а не отдельный канон продукта.

Правило приоритета:
- `tz_tactical_app.md` определяет целевое поведение системы;
- `spec-infra.md` уточняет, как это поведение обеспечивается технически;
- любые расхождения устраняются в пользу ТЗ с последующей синхронизацией этого файла.

## Время и аудит

- Все времена на сервере — UTC (`Instant`)
- У сущностей(users/squads/companies/orders/marker_types) должны быть `createdAt` и `updatedAt`, где это применимо
- Использовать Spring Data JPA auditing (`@CreatedDate`, `@LastModifiedDate`) для авто-заполнения

## Корреляция запросов

- Backend должен принимать `X-Request-Id` от клиентов
- Backend должен включать тот же `X-Request-Id` в:
  - response headers
  - log entries для запроса
- Если заголовок отсутствует — backend должен сгенерировать его.

## Логирование

- Логировать минимум:
  - request id
  - authenticated user id (если есть)
  - method + path
  - response status
  - duration
- Чувствительные данные:
  - никогда не логировать пароли
  - избегать логирования raw JWT

## База данных (канонический указатель)

Каноническая схема БД (MVP)

- Источник истины: миграции Flyway/Liquibase в репозитории (например, `V1__init.sql`, `V2__...`).
- Документация (ERD/описание таблиц) может генерироваться из миграций, но **не является** источником истины сама по себе.

Ключевые моменты:
- PostgreSQL — source of truth
- геопозиции хранятся историей (`user_geo_locations`) с индексом `(user_id, recorded_at desc)`
- markers содержат `expires_at` и должны фильтроваться по правилам active/expired
- squads и ограничения поддерживают отношения членства/привязки

## Redis — обязательный инфраструктурный компонент.
Redis используется как высокоскоростное временное хранилище
и механизм координации между backend-инстансами.

Redis не является источником истины.

Redis не должен использоваться
как постоянное хранилище доменных данных.

Источником истины всех доменных данных остаётся PostgreSQL.

Redis используется для следующих задач:

1. доставка WebSocket-событий между backend-инстансами
2. хранение информации об отозванных JWT-токенах
3. кэширование часто читаемых данных
4. хранение актуального состояния карты
5. распределённые блокировки фоновых задач

## Redis Event Bus для WebSocket

Система допускает работу нескольких backend-инстансов.

WebSocket-клиенты могут быть подключены к разным инстансам.

Для доставки событий между инстансами используется Redis.

Backend публикует события в Redis.
Все backend-инстансы подписываются на Redis-каналы
и ретранслируют события своим WebSocket-клиентам.

Redis используется только для передачи событий.
Постоянное хранение событий не выполняется.

Redis event bus используется для распространения событий:

- `MARKER_CREATED`
- `MARKER_DELETED`
- `ORDER_CREATED`
- `ORDER_STATUS_CHANGED`
- `USER_BLOCKED`
- `USER_STATUS_CHANGED`
- `GEO_POSITION_UPDATED`
- `SQUAD_MEMBERSHIP_CHANGED`
- `COMPANY_MEMBERSHIP_CHANGED`

## Отзыв JWT-токенов

JWT-токены имеют ограниченный срок действия.

Для немедленного отзыва токенов используется Redis.

Redis хранит список отозванных токенов.

Причины отзыва токена:

- logout пользователя
- блокировка пользователя
- удаление пользователя
- события безопасности

TTL записи Redis должен совпадать
со временем жизни соответствующего JWT.

При каждом защищённом REST или WebSocket запросе backend выполняет проверки:

1. проверка подписи и срока действия JWT
2. проверка отсутствия токена в Redis blacklist

## Кэширование данных

Redis используется как слой кэширования
для данных, которые часто читаются
и редко изменяются.

Redis cache не является источником истины.

Если запись отсутствует в Redis:

1. backend загружает данные из PostgreSQL
2. записывает их в Redis
3. возвращает результат клиенту

Кэшируются следующие данные:

- TacticalMarkerType
- правила типов маркеров
- membership пользователей в squad
- membership пользователей в company
- правила видимости
- базовая информация пользователя

Кэш должен инвалидироваться при изменении данных.

## Кэш состояния карты

Redis может использоваться для хранения
актуального состояния карты.

Цель — уменьшить количество запросов к PostgreSQL
при работе realtime-карты.

Redis может хранить:

- последнюю известную геопозицию пользователя
- активные тактические маркеры
- текущее состояние объектов карты

Исторические данные остаются только в PostgreSQL.

Redis хранит только актуальный срез данных.

## Фоновые задачи
 (MVP)

Истечение меток:
- Фоновый sweep каждые 1 минуту (настраиваемо) для обнаружения истёкших меток и эмита `MARKER_DELETED`.
- Sweep также может выполнять очистку/архивацию по выбору реализации.

## Распределённые блокировки

В системе существуют фоновые задачи.

Пример:

- периодическая очистка истёкших маркеров (marker sweep)

Если backend работает в нескольких экземплярах,
необходимо предотвратить параллельное выполнение
одной и той же задачи.

Для этого используется распределённая блокировка в Redis.

Перед выполнением фоновой задачи backend должен получить lock.

Если lock уже удерживается другим инстансом,
задача не выполняется.

## Deployment defaults (MVP)

- Java 21 + Spring Boot 4.x
- Postgres
- Redis
