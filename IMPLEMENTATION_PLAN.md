# План разработки MVP (для начинающего разработчика)

Цель: реализовать приложение по всей проектной документации, двигаясь от базового каркаса к полноценному функционалу, при этом в конце **каждого этапа** проект должен:

1. компилироваться;
2. запускаться;
3. давать проверяемый рабочий функционал.

---

## Этап 0. Подготовка каркаса проекта и среды

**Тема для подготовки:** основы Spring Boot (слои controller/service/repository), Docker Compose, Flyway, базовый JWT.

**Что делаем:**
- Поднимаем базовую инфраструктуру: backend + PostgreSQL + Redis.
- Создаём модульную структуру пакетов по `spec-structure.md`.
- Подключаем Flyway и заводим первичные миграции по текущей схеме.
- Добавляем health endpoint и минимальный smoke REST endpoint.

**Проверка этапа:**
- backend стартует;
- миграции применяются;
- простой endpoint отвечает `200`.

---

## Этап 1. Базовые cross-cutting механики (ошибки, время, аудит, request-id)

**Тема для подготовки:** обработка ошибок в Spring (`@ControllerAdvice`), DTO-валидация, логирование и MDC.

**Что делаем:**
- Вводим единый `ErrorResponse` (REST + задел под WS).
- Реализуем единые коды ошибок и формат `details.errors[]`.
- Стандартизируем время (`UTC`, `Instant`) и аудит (`createdAt/updatedAt`).
- Добавляем обработку `X-Request-Id`: принять/сгенерировать, вернуть в response, проставить в логи.

**Проверка этапа:**
- проект компилируется;
- API отдаёт каноничный формат ошибок;
- `X-Request-Id` наблюдается в ответе и логах.

---

## Этап 2. Auth + Users (MVP минимум)

**Тема для подготовки:** Spring Security, JWT (claims/ttl), password hashing.

**Что делаем:**
- Реализуем `POST /auth/register`, `POST /auth/login`.
- Реализуем `GET /users/me`, `PATCH /users/me`, `POST /users/me/alive`, `POST /users/me/dead`.
- В JWT добавляем claims, включая `tokenVersion`; проверку `tokenVersion` делаем через Redis.
- Учитываем `accountStatus` в доступе к защищённым операциям.

**Проверка этапа:**
- регистрация/логин работают;
- защищённые endpoints требуют валидный JWT;
- пользователь может менять профиль и `isAlive`.

---

## Этап 3. Squads (полный жизненный цикл)

**Тема для подготовки:** доменные инварианты, транзакции, ACL на уровне use-case.

**Что делаем:**
- Реализуем API отрядов: создание, просмотр своего, вступление, выход, кик, передача командира, роспуск.
- Строго соблюдаем инварианты: один пользователь = максимум один отряд, ровно один командир в отряде, удаление пустого отряда.
- Сразу публикуем доменные события в internal bus (позже подключим WS/Redis).

**Проверка этапа:**
- backend запускается и операции над отрядами проходят e2e;
- граничные сценарии (выход командира, выход последнего участника) покрыты тестами;
- бизнес-ошибки корректно мапятся в коды.

---

## Этап 4. Companies (полный жизненный цикл)

**Тема для подготовки:** управление связями агрегатов (squad-company), проверка полномочий командира.

**Что делаем:**
- Реализуем API рот: создание, просмотр своей, добавление/удаление отряда, роспуск.
- Учитываем инварианты: один отряд максимум в одной роте; пустая рота удаляется.
- Поддерживаем роль MODERATOR/ADMIN для административных действий.

**Проверка этапа:**
- сценарии «создать роту → добавить/убрать отряд → автоудаление пустой роты» проверяемы через API;
- компиляция и запуск стабильны.

---

## Этап 5. Marker types + Admin

**Тема для подготовки:** role-based access control, soft constraints и валидация справочников.

**Что делаем:**
- Реализуем admin API: изменение `accountStatus`, CRUD (в рамках spec) для типов меток.
- Внедряем эффекты изменения `accountStatus`: запрет REST/WS для BLOCKED/DELETED.
- Подготавливаем данные marker types как управляемый справочник из БД.

**Проверка этапа:**
- ADMIN/MODERATOR сценарии доступны и проверяемы;
- USER получает `403 FORBIDDEN` там, где требуется;
- смена `accountStatus` действительно блокирует доступ.

---

## Этап 6. Tactical markers

**Тема для подготовки:** доменные правила видимости, TTL/expiration, uniqueness policy.

**Что делаем:**
- Реализуем `POST /markers`, `GET /markers`, `DELETE /markers/{markerId}`.
- Соблюдаем `roleRestriction`, `canSendToCompany`, `uniquenessPolicy`.
- Вводим обработку истечения (`expiresAt`) и модель активности маркеров.

**Проверка этапа:**
- маркеры создаются/читаются/удаляются по правилам видимости;
- маркерные ограничения по роли и uniqueness проверяются интеграционно;
- функционал демонстрируется в работающем UI/через API-клиент.

---

## Этап 7. Orders

**Тема для подготовки:** конечные автоматы статусов, идемпотентность переходов.

**Что делаем:**
- Реализуем `POST /orders`, `GET /orders`, `PATCH /orders/{orderId}/status`.
- Поддерживаем канонические переходы `CREATED -> IN_PROGRESS -> COMPLETED`.
- Обеспечиваем корректное заполнение `completedAt`.

**Проверка этапа:**
- список активных/всех приказов работает;
- некорректные переходы отдают `INVALID_ORDER_STATUS`;
- сценарий «создать приказ → провести до completed» проверяем end-to-end.

---

## Этап 8. Geo + read-model карты

**Тема для подготовки:** append-only модели, cache-aside, read-model в Redis.

**Что делаем:**
- Реализуем `POST /geo/position` (история), `GET /geo/positions` (последние видимые позиции).
- Фиксируем интервал клиента 30 секунд как канонический для auto режима.
- Делаем Redis read-model последней позиции пользователя и fallback к PostgreSQL.
- Реализуем read-model видимости пользователей.

**Проверка этапа:**
- запись истории и чтение последних позиций работают;
- видимость (свой отряд + командиры отрядов своей роты) соблюдается;
- система остаётся рабочей при cache miss.

---

## Этап 9. WebSocket realtime + Redis event bus

**Тема для подготовки:** WebSocket протокол, pub/sub, delivery semantics и авторизация WS.

**Что делаем:**
- Поднимаем WS endpoint `/ws/events` с auth по JWT.
- Реализуем форматы EVENT/SUBSCRIBE/UNSUBSCRIBE/ACK/ERROR.
- Подключаем публикацию/подписку через Redis event bus между инстансами.
- Поддерживаем канонические eventType и автоподписки пользователя на релевантные каналы.

**Проверка этапа:**
- WebSocket соединение работает в локальном окружении;
- события от squad/company/markers/orders доставляются клиенту;
- отключённый/заблокированный аккаунт не может использовать WS.

---

## Этап 10. Фоновые задачи, distributed lock, доводка NFR

**Тема для подготовки:** планировщики Spring, distributed lock в Redis, эксплуатационные метрики.

**Что делаем:**
- Реализуем sweep истёкших меток (каждую минуту, configurable).
- Защищаем фоновую задачу Redis-lock'ом, чтобы не было параллельного выполнения на нескольких инстансах.
- Финализируем кэш-инвалидации, observability и контроль логирования чувствительных данных.

**Проверка этапа:**
- истёкшие метки обрабатываются автоматически и дают нужные события;
- при нескольких инстансах sweep выполняется одним владельцем lock;
- эксплуатационные требования выполнены.

---

## Этап 11. Финальная приёмка соответствия документации

**Тема для подготовки:** методика traceability matrix (требование -> тест/endpoint/сценарий).

**Что делаем:**
- Собираем матрицу покрытия: все разделы ТЗ + spec-domain + spec-api + spec-ws + spec-infra + spec-redis.
- Проводим полный regression:
  - unit-тесты доменных правил;
  - интеграционные тесты REST;
  - WS-интеграционные проверки ключевых событий;
  - smoke-проверка UI сценариев MVP.
- Отдельно фиксируем, что чат в ТЗ помечен как future feature и **не входит в MVP**.

**Проверка этапа:**
- приложение запускается, компилируется, основные сценарии работают;
- нет требований из текущих документов, оставленных без реализации;
- готов релизный кандидат MVP.

---

## Рекомендуемый порядок сложности (для junior)

1. Инфраструктурный каркас и единые технические правила.
2. Auth/Users.
3. Squad/Company как базовая доменная модель.
4. Marker types/Admin.
5. Markers/Orders.
6. Geo/read-model.
7. WebSocket + Redis event bus.
8. Фоновые задачи и финальная стабилизация.

Такой порядок снижает риск: сначала строится надёжный фундамент (ошибки, безопасность, аудит), потом доменная логика, затем realtime и эксплуатационные оптимизации.
